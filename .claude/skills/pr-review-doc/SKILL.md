# pr-review-doc — 実装PRのレビューガイド(図解 HTML)

実装 PR(特に本番コード = ③ プロダクト層のリポジトリ)を、
レビュアーが**差分を1行ずつ追わなくても「何が・なぜ・どこに入り・何を確認すべきか」**を
最短で掴めるよう、**自己完結の図解 HTML レビューガイド**に整える。exp-deck(報告スライド)の
「レビュー HTML 版」。認知負荷を下げ、レビューの往復と見落としを減らすのが目的。

## いつ使うか

- 本番/共有コードへの PR をレビューに出すとき(SME・他メンバのレビュー負荷を下げたい)。
- 変更が**経路のどこに入るか**(制御/データフロー)や、**変更ファイルごとに何を見るか**が
  非自明で、差分だけでは把握コストが高いとき。
- 「報告スライド」でなく「PR レビューの地図」が欲しいとき(共有スライドは exp-deck)。

## この資料の目的(コンサル的メッセージ管理 × レビュー支援)

読者=レビュアーの疑問の順に、**結論と "見るべき所" を先に**。差分の代替ではなく
**レビューの地図**(最終確認は PR の実差分)。事実(検証済み)と推測/要判断を必ず分ける。

## まず読者レベルを決める(較正 — 最初の判断)

**認知負荷は読者の前提知識に対して相対的**。同じ PR でも、読者が変われば最適な資料が変わる。
どちらのモードを作るかを最初に決める(両方作ってもよい):

- **SME簡潔版**(その分野の専門家向け): 削って最短。用語は前提とする。
  → 下の「必ず出す5点」+ `references/template.html`。
- **初学者リッチ版**(他分野・そのコードに不慣れなレビュア向け。例: 生物系メンバ): 目的から厚く、
  未知語をその場で日本語に開き、1ファイル/1関数ずつ解説する。
  → 下の「初学者リッチ版の構造と作法」+ `references/template.learner.html`。

> ⚠️ 「短く削る」は **SME 向けの最適化**。初学者には**未知語の圧縮が逆に負荷を上げる**。
> 迷ったら、読者がそのコード領域の専門家でなければ **初学者リッチ版**を選ぶ。

## 必ず出す5点(SME簡潔版の本体。不変)

1. **流れ/アーキ図** — 変更が**経路のどこに入るか**を一目で(リクエスト/データフロー、
   複数の入口があるなら入口ごとにレーン分け)。新規点と既存への差込点を色で区別。
2. **変更ファイル → 役割 → レビュー観点 → リスク** の表 — レビューの地図。新規/既存改修を
   区別し、各ファイルで**具体的に何を確認するか**とリスク(高/中/低)を書く。
3. **テスト証拠カバレッジマップ** — 各挙動を**リスク階級**(L1純ロジック/L2並行/
   L3ハードウェア固有で自動化不能)に割り、**テスト名 → assert → 結果**(CI green / soak保留 等)
   の表で示す。**「検証済み(4点目)」はこのマップから生成する**(自由記述で「検証済み」と書かない)。
   自動化できない L3 は**「未カバー」と明示**する(これがテスト証拠ゲート = Definition of Done)。
4. **検証済み / 要判断の分離** — 「ビルド緑・テスト・パリティ等の確定事項」と「未検証・
   設計上あなたの判断が要る点」を2カラムで明確に分ける(誇張しない。AGENTS.md 準拠)。
   ⚠️ **build-green ≠ behavior-verified**: CI コンパイル/単体緑と、実機挙動(soak等)は別物として書く。
5. **特に見てほしい点** — レビュアーに投げる技術的な問い(設計判断・トレードオフ・境界)。

## 不変ルール

- **自己完結 HTML**: Artifact の CSP は外部ホストを全遮断。CDN/webfont/外部画像/fetch 禁止。
  CSS/JS はインライン、画像は data URI。表・コード・図は `overflow-x:auto` で本文を横スクロールさせない。
- **ブランド**: 色を変えるときは `uv run .claude/skills/exp-deck/brand/tokens.py` で
  CSS を再生成(主要色: 紫 `#531872`/緑 `#4E9D69`/赤 `#C0392B`。テンプレのインライン CSS が内蔵)。
  意匠の単一ソースは `.claude/skills/exp-deck/brand/` — 各所で色を再定義しない。
- **事実と推測を分離**(5点目の問い、4点目の split、3点目のカバレッジマップ)。結論は条件付きで。
- **差分の代替でない**と明記し、**PR と根拠レポート(`<実験ID>-R###`)にリンク**する。
- Artifact は既定で非公開。**共有はユーザーが claude.ai 上で行う**(SKILL は生成まで)。

## 初学者リッチ版の構造と作法

読者がそのコード領域に不慣れなら、簡潔さより**厚く・順序立てて・用語を開く**方が負荷が下がる。
骨格 = `references/template.learner.html`。

固定の読み順(=レビュアーの疑問順)。**左に固定目次**で迷子にしない:

1. **この PR は何をするもの(目的)** — 専門用語ゼロで「何が壊れ、どう直すか」を平易に。
2. **先に用語を覚える(用語集)** — 出てくる専門語(ロック/コールバック/faulted 等)を
   その場で日本語に開く。比喩を使う(例:「lock =資源を1人ずつに制限する札」)。← 詰まりを外す肝。
3. **変更ファイルを1つずつ** — 表に圧縮せず、ファイルごとに「なぜ触ったか + 見るコツ」。
4. **中心のロジック(before/after)** — 「どう壊れていた → どう直した」を物語で。図を併用。
5. **関数ごとの変更(詳しく)** — 変わった関数ごとに「なぜこう変えた」+
   **「この場合はこうなる / この場合はこうできる」の場合分け**(正常/異常/注意で色分け)。
6. **テストの読み下し** — 「テスト済み」と書かず、各テストが何を確かめたかを1行日本語に。
7. **検証済み / 要判断 + 見てほしい点** — 事実とあなたの判断を分ける。

**作法(原理)**:
- **未知語は圧縮せず開く**(§2 用語集 + 本文の初出で説明)。← readability-review の初出定義と同趣旨。
- **1ファイル/1関数ずつ**。この読者には厚さが親切。惜しまない。
- **場合分けで書く**: 抽象説明より「X のとき → Y」が初学者に届く。
- **before/after** でバグと修正を対比する。
- **関数解説・場合分けは必ず実差分を読んで書く**(推測で埋めない。要約からの創作は禁止)。
- 共通ルール(build-green ≠ behavior-verified、L3 =「未カバー」明示、事実/推測分離)は
  初学者版でも必ず守る(むしろ読み下して強調する)。

## 手順

0. **読者レベルを決める**(上「まず読者レベルを決める」)。以降 2 が分岐する。
1. **読む**: 対象 PR(差分・変更ファイル一覧)と、根拠になる実験レポート(`experiments/<実験ID>/reports/`)。
   変更が「経路のどこに入るか」を把握(必要なら該当リポを read-only で確認)。
   **初学者リッチ版では関数レベルの差分まで必ず読む**(`git diff <base> <head> -- <file>`。
   場合分けの「この場合はこうなる」は実コードが根拠 — 要約から創作しない)。
2. **埋める**:
   - **SME簡潔版** → `references/template.html` をコピーし、5点を埋める。ヘッダに PR 番号・
     ブランチ・base・「既定で無害か(挙動変化の有無)」を明記。流れ図はレーン/ノード
     (CSS ボックス+矢印)。ファイル表は新規(新)/改修(改)を明示、観点は具体的に、
     リスク高の行(アセンブリ境界・fail-open/closed・状態機械・並行・破壊的)を上に。
   - **初学者リッチ版** → `references/template.learner.html` をコピーし、7セクション
     (目的 → 用語集 → ファイル毎 → before/after → 関数毎の場合分け → テスト読み下し →
     検証済み/要判断)を埋める。用語をその場で開き、関数の場合分けは実差分から書く。
3. **公開**: `artifact-design` スキルを読んでから、埋めた HTML を **Artifact** で公開
   (`file_path` に HTML、`favicon` に絵文字)。技術レビュー文書=**端正・情報設計重視**の treatment
   (派手にしない)。表紙で PR/挙動変化/検証状況を先に出す。
4. **渡す**: Artifact リンクをユーザーに渡す(SendUserFile ではなく Artifact の URL)。
   PR には「レビューガイドあり(Artifact・共有はユーザー)」を1行コメントしてよい。作業は lab-log に残す。

## 仕組みと中身の分離

- **仕組み(不変の骨格)= `references/template.html`**(SME簡潔版: 5点の構造 + 流れ図の
  ボックス/矢印プリミティブ)と **`references/template.learner.html`**(初学者リッチ版:
  固定目次 + 7セクション + 用語集/ファイルカード/関数の場合分けブロック)。両方ブランド色を
  インライン CSS で内蔵。ここに PR 非依存の型を集約。
- **中身(PR 個票)= 都度埋めて Artifact 化**。テンプレの構造を保ち、色・並びは変えない。
- 型を拡張したくなったらこの SKILL.md と該当テンプレを直す(個票に骨格を持ち込まない)。
