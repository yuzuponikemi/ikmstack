# readability-review — レポートの自走性(self-contained)を独立レビューする

個別レポート(`reports/` 配下の一次記録)のゴールは、**その分野の初心者(＝自分の専門でないメンバー)が
その 1 本を読んで理解できる**こと(正本: docs/conventions/reporting.md「読みやすさのゴール」)。
だが執筆者は前提を暗黙に共有してしまい、**R001 / R002 でしか定義していない固有名詞・略語を、R003 で
無定義のまま使う**ことが起きる。読み手は「その 1 本」を開いただけでは意味が取れず、他レポートを
読みに行く羽目になる。このスキルは、その**自走性の破れを検出して直す**ための独立レビュー。

## 核となる仕掛け(なぜ効くか)

レビュー用サブエージェントに **対象レポート 1 本だけ** を渡す(兄弟レポート・`PLAN.md`・`REPORT.md`・
KB を**見せない**)。すると、R001 でしか定義されていない語は、**R001 を見られないレビュアーには
必ず分からない** → **兄弟レポート依存が自動的に炙り出される**。維持する用語リストは要らない
(隔離そのものが判定器になる)。

## ペルソナ(何を指摘し、何を指摘しないか)

サブエージェントは「**他分野の同僚**」を演じる。複数分野が交差する現場で、
自分の専門でない領域を読む新人、というイメージ。**素人ではない**(一般的な専門語は知っている)。

- **知っている＝指摘しない(一般語)**: 分野横断で通用する技術・統計・数学の語。
  例: MLP, ニューラルネット, AUC, ROC 曲線, SVM, 標準偏差(sd), 変動係数(CV), 相関係数(r),
  中央値, 回帰の傾き/切片, p 値, フーリエ変換 など。
- **知らない＝定義が無ければ指摘(固有語)**: プロジェクト/製品に固有の固有名詞・略語・社内呼称。
  例: 製品/装置名とその号機表記, 部位・信号のプロジェクト内呼称, 独自指標・定数名,
  工程・フェーズ名(この文脈でしか通じない「Phase 3」「Daily QC」等),
  ファイル/チャンネル/ステップの固有名, プロジェクト内の「x を y に換算」的な略記。
- **迷ったら**「他分野の新人がこの 1 本だけ読んで分かるか?」で決める。分からなければ指摘する。

## 手順

1. **対象レポートを特定**する(引数、または直近で書いた/触れた `reports/` 配下の一次記録)。複数あれば 1 本ずつ回す。
2. **隔離レビュー**: サブエージェント(Explore で可)を 1 体起動し、**対象レポートの本文だけ**を渡す。
   - **兄弟レポート・`PLAN.md`・`REPORT.md`・KB を渡さない**(渡すと仕掛けが壊れる = 最重要アンチパターン)。
   - 指示内容:
     - 上記「他分野の同僚」ペルソナで通読する。
     - **このレポート単体で意味の取れない固有名詞・略語を、初出順に列挙**する。
     - 各項目に `{用語, 初出の逐語引用(できれば行番号), なぜ分からないか(1行), 推奨する初出定義(1行)}`。
     - 一般語(上記リストの類)は挙げない。
     - あわせて**新語の役割跨ぎ検査**(下の節)の 3 観点 — 初出定義の欠落・役割跨ぎ・
       作業ラベル見出し — に該当する箇所も列挙する。
     - 出力は**指摘リストのみ**。本文の書き換えはしない(書き換えは主エージェントが行う)。
3. **取捨**: 返ってきた指摘を主エージェントが精査し、一般語の誤検知を捨て、**正当な指摘だけ残す**。
4. **書き直し**: **第一手は本文そのものを平易に書き直すこと**(語彙集を前に足すことではない)。
   自走性は**地の文が意味を運ぶ**ことで達成する。優先順に:
   - **(a) 初出箇所にインライン定義を挿入**(reporting.md「略語は初出でフルスペル+意味」)。
     略語 → 「フルスペル(意味)」。例: 「GMI(Ghost Motion Imaging、本プロジェクトの信号取得方式)」。
     固有名詞 → 1 行で何かを補う。例: 「VS01(装置の 1 号機)」「Phase 3(実機で流速を振る計画段階)」。
   - **(b) 冒頭に短い平易な導入文(散文)** を置き、読み手が本文に入る前に「何を・なぜ・何がわかったか」を
     つかめるようにする(表ではなく地の文)。密な結論は平易な言葉に開く。
   - **(c) それでも残る“地の文に溶けない生の識別子”だけ**、冒頭にごく小さな記号メモを置く
     (例: コード上の変数/状態名 `SR2F`・`T602_I`、繰り返し出るセンサ ID 対応)。**大きな語彙表の前置きはしない**。
     語数が多いと感じたら、それは語彙表の合図ではなく、**本文の語を減らす/1トピック1レポートに分ける**合図
     (reporting.md「量が増えたら話題ごとに分ける」)。
   - **「○○は R001 参照」で前提を省かない** — 定義は**この 1 本の中に**置く(自走性の要件)。
   - リビング文書 `REPORT.md`(現状サマリ)も同様: 前置きの語彙表でなく、導入の散文＋要語のインライン定義で開く。
5. **再チェック(任意)**: 指摘が多かった、または大きく直した場合は、同じ隔離レビューをもう一度回して残りを確認する。
6. **報告**: 指摘件数・採用/棄却・挿入した定義を表でユーザーに示す。

## 一般語 vs 固有語(早見表)

| 指摘しない(一般語・そのままでよい) | 指摘する(固有語・初出で定義が要る) |
|---|---|
| MLP, AUC, ROC, SVM, sd, CV, 相関係数 r, 中央値, 傾き/切片, p 値 | 製品/装置名・号機表記, プロジェクト固有の信号・部位呼称, 独自指標/定数名, Phase 3・Daily QC 等の工程名, プロジェクト内の x→y 略記 |

## 新語の役割跨ぎ検査(固有語検査への追加観点)

未定義の固有語(上)に加えて、**執筆者がその場で導入した新語(造語)は、定義があっても危うい** —
一つの語が開始条件・事象・値を行き来すると、読み手ごとに別の対象を想像し、その語を土台にした
設計・命名まで汚染が波及する。隔離レビューのサブエージェント指示に次の 3 観点を含める:

- **初出定義の欠落**: 新語(既存の確立語・プロジェクト用語集の正準語でない略称・名詞句)に、
  初出の定義文「X とは〜を指す」が無い。
  <!-- policy:new-term-referent-first@8b08bf1b -->
- **役割跨ぎ**: 一つの語が複数の役割(開始条件/状態/事象/値/記録/目的/手段)を跨いで
  使われている(→ 修正は語を分ける)。
- **作業ラベル**: 見出し・結論が、目的・対象・判断を省いた抽象名詞句になっている
  (例: 「観測を一つに集める」型 → 具体文に開く)。

修正後、ドメインの語として今後も使う新語があれば、プロジェクトの用語集(正本があるならそこ)への
追記(昇格)をユーザーに提案する。
正本: docs/conventions/reporting.md「新語(造語)の導入規律 — 語より先に指示対象」

## アンチパターン

- **サブエージェントに兄弟レポートや `REPORT.md` を渡す** → 仕掛けが壊れ、依存を検出できない。**1 本だけ**渡す。
- **用語集/allowlist を作って維持する** → 保守負担(単独稼働・エントロピー最小の方針に反する)。
  ペルソナ判断で足りる(隔離が判定器)。
- **一般語まで律儀に展開する** → ノイズ。MLP を毎回綴り直さない。読み手は他分野の「新人」であって「素人」ではない。
- **指摘を機械的に全部採用する** → 一般語の誤検知は捨てる。主エージェントの取捨が品質の対価。
- **冒頭に大きな語彙集/用語表を前置きして済ませる** → 読み手は結論の前に表を読まされ、結局本文へ戻って
  クロス参照する(自走性は本文の文で達成すべき)。**本文の書き直し(a)(b)を第一手にし、記号メモ(c)は
  地の文に溶けない生の識別子だけ最小限**に。表への逃げは「本文の語が多すぎる」合図(=語を減らす/分割する)。
