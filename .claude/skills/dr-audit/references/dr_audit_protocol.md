# dr-audit 事実検証プロトコル・詳細ガイド

本ドキュメントは、エージェント生成レポートの数値や事実を独立検証するための詳細手順とスクリプトの使い方を定めています。

---

## 1. 検証プロセスの設計思想

自己申告の確信度ラベルは独立検証の代わりになりません。執筆エージェントの出力したテキストを直接信じず、**「別エージェント (dr-verifier) による出典の再取得」**と**「決定論スクリプトによる数値の再計算・整合チェック」**を強制します。

### 受入ゲート (`dr_gate.py`) の強制ルール
- 受入ゲートは本プロセスの最後に**必ず実行**しなければなりません。
- ゲートの実行が PASS するまで、レポートの作成は完了と見なされません（FAIL のまま完了としないこと）。
- ※グローバル Stop hook は未成熟なゲートによる普段の作業ブロックを防ぐため、デフォルトでは無効化されています。手動またはスキル内での一巡検証を厳格に実施してください。

---

## 2. 前提と準備

### 関連ツール
- **決定論スクリプト**: [`tools/dr/`](../../../tools/dr/) (すべて標準ライブラリのみで動作)
  - `validate_ledger.py` — 台帳のスキーマ/必須列検証
  - `numeric_compare.py` — 派生値の決定論的再計算
  - `ledger_to_prose_check.py` — 散文（Markdown）と台帳の整合チェック
  - `sampling_select.py` — 補足主張のリスク加重サンプリング
  - `dr_gate.py` — 受入ゲート判定
- **独立検証者**: サブエージェント [`dr-verifier`](../../agents/dr-verifier.md)
- **台帳スキーマ仕様**: [`tools/dr/claims_schema.md`](../../../tools/dr/claims_schema.md)

---

## 3. 検証手順 (5つのステップ)

### ステップ1: 主張台帳 (`claims.jsonl`) の用意と基本検証
- 対象レポートの数値や固有名詞の断定を 1行1主張として `claims.jsonl` に書き起こします。
- 台帳のスキーマ検証を実行します：
  ```sh
  python tools/dr/validate_ledger.py <台帳パス>/claims.jsonl
  ```
  ※エラーが出た場合はスキーマに従って修復します。

### ステップ2: 判断駆動主張の独立検証 (`dr-verifier` の呼び出し)
- 重要度が `risk=decision_driving` の主張について、独立検証サブエージェント `dr-verifier` を呼び出します。
- **重要**: 独立性を担保するため、検証者には `claim_id`, `subject`, `attribute`, `value_raw`, `value_num`, `unit`, `source_url` **のみ**を渡し、執筆者の `verbatim_quote`（引用）や注記は渡しません。
- 返された検証結果 JSON (`verification`, `citation_axes`, `entity_check`) を台帳に書き戻します。
- 補足的主張 (`risk=supporting`) は、サンプリング選定スクリプトを実行して選ばれた行のみを検証します：
  ```sh
  python tools/dr/sampling_select.py <台帳パス>/claims.jsonl
  ```

### ステップ3: 派生値の決定論的再計算 (Recompute)
- `python tools/dr/numeric_compare.py <台帳パス>/claims.jsonl`
- **mismatch 時の調査手順**: 
  1. 出典の導出基準（分母や入力となる指標の定義）を確認します。
  2. 台帳の `derivation.vars` や `formula` の定義誤り（台帳のバグ）か、一次ソースの値自体の誤りかを切り分けます。
  3. 台帳側の定義が誤っている場合は `vars` を修正します。

### ステップ4: 散文（Markdown）と台帳の相互追跡
- Markdown レポート内の数値に `(claim:cNNN)` のマーカーを付与し、台帳と紐づけます。
- 散文との整合性チェックを実行します：
  ```sh
  python tools/dr/ledger_to_prose_check.py <散文ファイル> <台帳パス>/claims.jsonl
  ```
- 散文中の記述と台帳の値の乖離（E3: 数値ドリフト）はすべて修正します。

### ステップ5: 受入ゲートの実行
- 最後に必ず受入ゲートスクリプトを実行します：
  ```sh
  python tools/dr/dr_gate.py <台帳パス>/claims.jsonl
  ```
- **PASS**: すべての `decision_driving` が検証済み、かつ不良率が許容基準（AQL）以下、かつ引用整合性が取れている場合に判定されます。
- **FAIL**: ゲートを通過しなかった場合、指摘された箇所をステップ2〜4に戻って修正・再検証し、PASS するまで繰り返します。

---

## 4. プロセスの限界

- `dr-verifier` のWebFetch経由の再取得は完全に決定論的ではないため、表記揺れが発生する可能性があります。
- 決定論的に検証可能な領域は、「数値・単位の完全一致」「派生値の再計算」「散文↔台帳のマーカー追跡」の範囲に限定されます。

---

## 5. Subagent (サブエージェント) を用いた実行規約 (トークン節約)

親エージェントは自身で `claims.jsonl` や Markdown 原稿を読み込んではいけません。会話履歴のトークン肥大化を防ぐため、必ず一時的な **Subagent** を起動し、以下の指示テンプレートを用いてタスクを完全に委譲してください。

### Subagent 起動プロンプトテンプレート：
```
以下の手順で、レポートの事実・数値の検証（dr-audit）を自律的に遂行してください：

1. 対象レポート: [対象レポートのファイルパス]
2. 対象主張台帳: [claims.jsonl のファイルパス]

タスク内容：
1. `python tools/dr/validate_ledger.py` を実行してスキーマを確認し、エラーがあれば台帳を修復してください。
2. 台帳の `decision_driving` 主張に対し、独立検証エージェント `dr-verifier` を呼び出して検証を実行してください。補足主張は `sampling_select.py` の選択結果に基づき検証してください。
3. `python tools/dr/numeric_compare.py` で派生値の再計算・照合を実行し、ミスマッチがあれば原因を調べて台帳を修正してください。
4. `python tools/dr/ledger_to_prose_check.py` で散文レポートと台帳の整合性を確認し、不一致（数値ドリフト）があれば修正してください。
5. 最後に `python tools/dr/dr_gate.py` を実行し、PASS するまで自律的に修正と再検証をループしてください。

完了後、以下の形式のみで親エージェントに最終報告を行ってください。途中のデバッグログや JSONL データ等の長大なテキストは返さないでください：
---
■ 検証結果: [PASS / FAIL]
■ 修正された主張の概要:
- cNNN: [修正概要]
■ 最終的なゲート判定出力の抜粋
---
```
親エージェントは、Subagent から返された上記のサマリー報告のみをチャット履歴に残し、次の手順に進んでください。
