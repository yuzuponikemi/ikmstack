# 調査(ディープリサーチ)の規約

> reporting.md の**調査版**。実験(自分でデータを取る)ではなく
> **調査(他人の一次情報を集めて結論を出す)**をするときに開く。
> 「書いた数値が出典と合うか」の検証は `tools/dr/` と dr-audit スキルが正本。
> ここはその**手前** — 何を調べ、何を集め、どこで閉じるかの規律。

## なぜ実験と別の規約が要るか

実験の再現性は「生データ(Google Drive) + 生成スクリプト(git) + commit SHA(MANIFEST.md)」で
担保される(AGENTS.md 三大原則#1)。調査の「生データ」は**外部の一次情報**で、実験には無い
3つの失敗様式を持つ:

1. **消える・書き換わる**(link rot)。取得日を書いても、後から同じものは読めない。
2. **網羅したかどうかが自己申告になる**。実験は測ったか測っていないかが明白だが、
   調査は「探していない」と「探したが無かった」が外から区別できない。
3. **支持証拠だけ集めても形が整う**。反証を探さなくても、レポートは完成して見える。

既存の受入ゲート(`tools/dr/dr_gate.py`)が守るのは「**書いた**主張が出典と合っているか」だけで、
「**書かなかったこと**」は素通りする。撤回類型の `absence-claim`(探索不足のまま「無い」と断定)が
示すのはこの失敗様式で、調査ではこれが撤回の主因になる。だから調査には
**網羅の側のゲート**を別に置く。

## 3つの台帳(1機能=1権威)

調査は台帳を3つ持つ。役割が違うので統合しない。置き場は実験の `reports/` 直下
(`claims.jsonl` と同じ場所)。いずれも JSONL = テキストなので git にコミットできる(三大原則#1)。

<!-- policy:living-vs-primary@134848f4 -->
| 台帳 | 役割(1機能) | スキーマの正本 |
|---|---|---|
| `questions.jsonl` | 下位問いと**決着条件**。調査の骨格 | `tools/dr/research_schema.md` |
| `sources.jsonl` | **探索の記録**。採ったものだけでなく**採らなかったもの**も | `tools/dr/research_schema.md` |
| `claims.jsonl` | 主張・出典・検証。既存 | `tools/dr/claims_schema.md` |

3つは `question_id` / `source_id` で相互に解決する。解決しない ID はゲートが止める。

## 下位問いと決着条件(正本)

**決着条件を書いてから調べる。** 決着条件とは「何が観測・確認できたらこの問いを閉じてよいか」を
事前に書いた文を指す。これが無い問いは、探索がいつまでも終わらないか、疲れた時点で恣意的に閉じる。

- 主問い(research question)1つを、**独立に閉じられる下位問い**に分解して `questions.jsonl` に書く。
  下位問いは `Q1`, `Q2`, … の連番 ID を持つ。
- 各下位問いに **`closing_condition`(決着条件)** を必ず書く。書けない問いは、まだ問いとして
  成立していない — 分解し直すか、`status: exploratory` として「決着させない探索」だと明示する。
- 各下位問いは `status` を持つ: `open`(調査中) / `closed`(決着) / `abandoned`(打ち切り)。
  **`closed` にできるのは決着条件を満たしたときだけ**で、材料が尽きたときは `abandoned` にし、
  理由を `note` に書く(打ち切りを決着と偽らない)。
- **`open` / `abandoned` のまま残った問いは `REPORT.md` に open question として明記する。**
  調査で最も価値のある情報は「分からなかったこと」で、これを落とすと読み手は
  網羅されたと誤解する。

## 出典の格付けと独立性(正本)

**独立した2本**が判断駆動の下限。ただし「2本」を数える前に格付けと孫引きを畳む。

- **格付け(`tier`)**: `primary`(一次 = 原論文・一次統計・規格・当事者の一次発表) /
  `secondary`(二次 = 解説記事・レビュー・報道) / `tertiary`(三次 = まとめサイト・百科事典) /
  `vendor`(利害関係者 = 販売元・当事者の宣伝資料)。
- **孫引きは独立ソースに数えない。** 二次情報が別の原典を引いているなら、`derived_from` に
  その原典の `source_id`(未取得なら URL)を書く。独立本数は **`derived_from` で畳んだ後**に数える。
  同じ原典を引く3本の記事は独立1本である。
- **`vendor` 単独で判断駆動の問いを閉じない。** 利害関係者の主張は、独立ソースの裏づけと
  対にして初めて根拠になる。
- **数値・仕様は一次まで遡る。** 二次情報の数値を引く場合は、原典を当たれなかったこと自体を
  `note` に書く(遡れないことは欠陥ではないが、隠すと欠陥になる)。

## 出典はスナップショットを取る(link rot)

**取得した時点のページを保存する。** `source_accessed`(取得日)だけでは再現できない。

- 保存先は Google Drive の当該実験フォルダ配下 `sources/<source_id>.<ext>`。
  **git には入れない**(三大原則#1: git はテキスト + 生成スクリプトだけ)。
- `sources.jsonl` の `snapshot` にその相対パスを書く。台帳はテキストなので git に載り、
  実体は Drive にある — 実験の「生データは Drive・台帳は git」と同じ構造。
- スナップショットを取れなかった出典(有料壁・動的ページ)は `snapshot: null` のまま、
  `note` に取れなかった理由を書く。**取れなかったことを黙って空欄にしない。**

## 反証探索を記録する(正本)

**支持証拠だけで問いを閉じない。** 反証探索(refutation search)とは、自分の作業仮説を
**否定する側**の情報を意図的に探す作業を指す。やったことは台帳に残らないと検証できないので、
記録を成果物にする。

- 各主張は `stance` を持つ: `supports`(下位問いの作業仮説を支持) / `refutes`(反証) /
  `neutral`(どちらでもない・文脈)。
  - `stance` は**主張が下位問いに対して取る立場**。`citation_axes.supports`(出典が主張本文を
    裏づけるか)とは別の軸なので混同しない。
- **`closed` の下位問いは、反証側の痕跡を1つ以上持つ**。痕跡として認めるのは次のどちらか:
  1. `stance: refutes` または `neutral` の主張が `claims.jsonl` に1件以上ある、または
  2. `sources.jsonl` に、その問い向けに**反証を狙って探し、該当が無かった**記録がある
     (`decision: rejected` + `found_via` に検索クエリ + `decision_reason` に棄却理由)。
- 探して見つからなかったことは**成果**である。`sources.jsonl` に残っていない
  「探したつもり」は、`absence-claim` 型の撤回として後から必ず返ってくる。

## 台帳を先に作る(散文は台帳から導出する)

**読みながら台帳を埋め、台帳から散文を書く。** 逆順(散文を書いてから数値を台帳に書き起こす)は
dr-audit の事後監査としては成立するが、調査では網羅の判断材料が最後まで存在しないことになる。

- 収集フェーズで `sources.jsonl` → `claims.jsonl` の順に埋める。執筆はその後。
- 散文中の判断駆動数値には `(claim:cNNN)` マーカを**執筆時に**打つ
  (マーカ規約の正本は reporting.md「検証ゲート(.dr-gate)と claim マーカ」)。
  台帳が先にあるので、調査ではマーカ付けのコストがほぼゼロになる。
- これにより dr-audit は「台帳を作る作業」から「既にある台帳を検証する作業」に変わる。

## 網羅ゲート(正本)

受入ゲート `dr_gate.py` が**書いたものの正しさ**を見るのに対し、網羅ゲート
`dr_coverage.py` は**書かなかったことの穴**を見る。調査は両方を通して初めて受入可とする。

```sh
python3 "$(cat ~/.ikmstack/install-path)/tools/dr/dr_coverage.py" <reports>/questions.jsonl
```

検査する5条件(いずれか1つでも欠ければ FAIL):

| ID | 条件 |
|---|---|
| K1 | `closed` の下位問いは `decision_driving` の主張を1件以上持つ |
| K2 | `closed` の下位問いは、`derived_from` で畳んだ後の**独立ソースを `min_independent_sources`(既定 2)本以上**持つ |
| K3 | `closed` の下位問いは**反証側の痕跡**を持つ(上の「反証探索を記録する」の 1 か 2) |
| K4 | すべての `question_id` / `source_id` 参照が実在の台帳行に解決する |
| K5 | `open` / `abandoned` の下位問いが散文に open question として現れる(`--prose` 指定時のみ) |

<!-- policy:dr-gate-opt-in@fd4434e1 -->
`.dr-gate` に `questions:` を書いた実験は、commit 時の軽量ゲートでも K1〜K4 が走る
(K5 は `prose:` も併記したときだけ)。opt-in の仕組みそのものは reporting.md
「検証ゲート(.dr-gate)と claim マーカ」が正本。

## いつ回すか

<!-- policy:verify-before-sharing@38a1a7de -->
reporting.md「いつ検証するか — 共有前ゲート」と同じタイミング(平場では回さない)。
ただし調査では**順序が決まっている**:

1. `/dr-plan` — 主問いを下位問いに分解し、決着条件を書く(`questions.jsonl`)
2. `/dr-collect` — 探索し、`sources.jsonl` → `claims.jsonl` を埋める(反証探索を含む)
3. `/dr-synth` — 台帳から論証を組み、散文にする
4. `dr_coverage.py`(網羅) → `/dr-audit`(出典照合) の順に2つのゲートを通す

**網羅ゲートを先に通す。** 穴だらけの調査の数値を出典照合しても、
「正しく引用された不完全な結論」になるだけで、費用の掛けどころを間違える。

## 実験の規約との対応

| 実験(reporting.md) | 調査(この文書) |
|---|---|
| `PLAN.md` の仮説・成功条件 | `questions.jsonl` の下位問いと決着条件 |
| `MANIFEST.md` の commit SHA | `sources.jsonl` の `snapshot` + `accessed` |
| 生データ(Drive)+ `regenerate.sh` | 出典スナップショット(Drive)+ 台帳(git) |
| `dr_gate.py`(書いた数値の正しさ) | `dr_coverage.py`(書かなかったことの穴) |

文書の役割分担(リビング文書 vs 一次記録・R 番号)は reporting.md がそのまま適用される。
調査だからといって `REPORT.md` を複数持たない。
